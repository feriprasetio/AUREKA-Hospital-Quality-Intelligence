# NARA AI — Clinical Intelligence and Provider Governance

## 1. Purpose

NARA AI is the AUREKA hospital-intelligence workspace. It provides a single AI entry point for quality management, patient safety, risk management, clinical decision support, operational summaries, research/statistics support, and ICD-10 coding governance.

NARA uses a server-side Supabase Edge Function gateway. Provider keys are never placed in the browser bundle or returned to the client.

## 2. Provider orchestration

The gateway supports five providers:

1. Groq
2. NVIDIA
3. Gemini
4. DeepSeek
5. LLM7

The default route order is configured by `AI_PROVIDER_ORDER` (default: `groq,nvidia,gemini,deepseek,llm7`). A provider is eligible only when its server-side secret exists. The router falls through to the next provider after provider/model availability, rate-limit, timeout, quota, or server errors. `AI_ENABLE_DEEPSEEK=false` and `AI_ENABLE_LLM7=false` are explicit kill switches. The order can be adjusted without changing the frontend.

All five adapters being supported does not mean every provider is healthy or has usable quota at every moment. A secret's existence is not evidence that a vendor request has succeeded; provider availability must be measured from runtime logs and authenticated test requests.

## 3. Data access model

NARA does not receive unrestricted database credentials and does not issue arbitrary SQL generated by an LLM. Data access is through the authenticated user's Supabase JWT and permission-aware backend functions. SQL functions enforce the user's role and permitted room scope.

The general workspace context uses aggregate summaries from AUREKA modules. The context intentionally excludes direct patient identifiers, staff names, and raw patient-level event rows. Examples include:
- Manajemen Risiko: totals and risk-level distributions.
- Rencana Tindak: status and overdue totals.
- Keselamatan Pasien: incident totals and suppressed category counts.
- Mutu Klinis: logbook submission counts by unit and period.
- Governance/Infographics: aggregate values via `aureka_gov_infographics_summary_secure`.

The context is not a universal raw-data dump. Each module is included only through its verified, permission-appropriate aggregate.

## 4. Clinical diagnosis analytics

The function `public.aureka_nara_clinical_summary(p_year,p_room,p_limit)` calculates diagnosis rankings inside PostgreSQL. It prefers encounter-level records from `aureka_quality.quality_records` where `measurement_grain='patient_episode'`. The normalized medical record number (No. RM) is used only inside the secured SQL function for distinct-patient deduplication. It is never returned in the result or sent to an external model.

If episode records are not yet present, the function falls back to `aureka_quality.patient_index.diagnosis_terakhir`, which provides only one latest diagnosis per indexed patient. The response explicitly labels this basis and does not misrepresent it as all encounter-level diagnoses or all DPJP history.

### Verified production data availability at implementation

- Patient index: **10,913** rows.
- Rows with a populated latest diagnosis: **1,747**.
- Patient-episode rows in `quality_records`: **0**.

Therefore, the current deployment can calculate a preliminary ranking from latest diagnoses per patient. It cannot yet produce a complete "top diseases by all visits/episodes" ranking, or a complete DPJP diagnosis history. Those results require encounter-level clinical records to be entered/linked in AUREKA.

The clinical summary:
- enforces role and room scope;
- uses No. RM only inside the database for internal deduplication;
- excludes obvious identifier-like diagnosis values and exact patient-name matches;
- suppresses diagnosis groups with fewer than five patients;
- writes a PHI-free access audit record; and
- returns aggregate diagnosis labels and counts only.

A top-disease query is routed directly to this SQL function. The resulting diagnosis aggregate bypasses all external LLM providers.

## 5. ICD-10 governance

A controlled dictionary `aureka_quality.nara_icd10_dictionary` stores the mapping from diagnosis labels to ICD-10:
- `proposed`: suggested but not validated;
- `validated`: reviewed and approved;
- `rejected`: not accepted.

NARA does not infer a validated code from ambiguous abbreviations. A mapping becomes `validated` only after an authorized reviewer provides:
- the ICD-10 code;
- the official diagnosis title; and
- a validation reference.

The reviewer interface and server-side functions are restricted to Super Admin (`ADMIN`) and Komite PMKP (`PMKP`). PMIK/DPJP validation should be part of the hospital's formal coding workflow before codes are relied upon for official reporting, claim submission, or clinical decisions.

The deployed dictionary currently starts empty; mappings need to be reviewed and entered. ICD-10 release selection must be aligned to the hospital's approved coding policy and applicable national rules.

## 6. Privacy, security, and governance

No patient name or No. RM is sent to Groq, NVIDIA, Gemini, DeepSeek, or LLM7. NARA uses internal No. RM only for database deduplication, behind Supabase authorization, and returns aggregate results. Database tables for the ICD-10 dictionary and access audit have RLS enabled and direct API grants revoked; access is mediated by restricted functions.

This implementation is a technical control, not a substitute for the hospital's privacy governance. Before expanding to broader clinical-data processing, the hospital must establish lawful basis, access approvals, a Data Protection Impact Assessment where required, vendor/data-processing terms, retention rules, incident response, access review, and validation of any cross-border processing.

## 7. Known constraints and next operational steps

1. Populate encounter-level patient episode data and validate the link to DPJP/source records.
2. Confirm diagnosis field semantics and data quality for each unit's source form.
3. Review and validate high-frequency diagnosis labels in the ICD-10 queue with PMIK/DPJP.
4. Run authenticated role-based UAT for Super Admin, PMKP, unit PIC, and other authorized users.
5. Exercise each configured provider using non-PHI synthetic prompts; record success, latency, quota/rate-limit response, and fallback behavior.
6. Monitor the PHI-free NARA access audit and Supabase security/performance advisors.

NARA must always state whether a clinical ranking is based on unique patients, episodes, or another defined denominator. It must not present latest-diagnosis-per-patient counts as visit/episode counts.
